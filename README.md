# Customer Churn Prediction

An end-to-end machine learning project that predicts whether a telecom
customer is likely to churn (cancel their service), using account details
like contract type, tenure, and monthly charges.

## Overview

This project goes a step further than a typical classification task: the
target is **imbalanced** (far more customers stay than leave), so the
project focuses specifically on handling that properly — using SMOTE and
F1-score instead of relying on plain accuracy, which would be misleading
here.

**Dataset:** ~7,000 telecom customers (IBM Telco Customer Churn dataset),
with a mix of numeric (tenure, charges) and categorical (contract type,
internet service, payment method) features.

## What this project demonstrates

- Cleaning a column stored as text that should be numeric (`TotalCharges`)
- Building a reusable preprocessing pipeline with `ColumnTransformer`
- Recognizing and handling class imbalance with **SMOTE**
  (`imbalanced-learn`)
- Comparing models using **F1-score**, not accuracy, since accuracy is
  misleading on imbalanced data
- Hyperparameter tuning with `GridSearchCV`
- Saving a trained pipeline with `joblib` for later reuse
- Predicting on a brand new, unseen customer

## How to run

1. Set up a virtual environment:
   ```bash
   python -m venv venv
   source venv/bin/activate      # Windows: venv\Scripts\activate
   pip install -r requirements.txt
   ```

2. Train the model:
   ```bash
   python src/train.py
   ```
   Loads data directly from a public URL, cleans it, applies SMOTE to
   handle imbalance, compares models, tunes the best one, evaluates it, and
   saves the final pipeline to `models/churn_model.pkl`.

3. Predict on a new customer:
   ```bash
   python src/predict.py
   ```
   Loads the saved model and predicts on a sample customer defined in the
   script — edit the values there to try your own.

## Why imbalance handling matters here

Roughly 73% of customers in this dataset stay, 27% churn. A model that
just predicts "stays" every time would already score 73% accuracy while
being completely useless for the actual business goal: catching churners
before they leave. This project uses **SMOTE** (synthetic oversampling of
the minority class) during training and **F1-score** for evaluation, so
the model is actually judged — and optimized — on whether it catches
churners, not just on raw accuracy.

## What I'd improve next

- Try threshold tuning (adjusting the probability cutoff for "churn")
  instead of the default 0.5
- Add a cost-sensitive evaluation (false negatives — missed churners —
  are usually more costly to a business than false positives)
- Build a small Streamlit dashboard for live predictions
